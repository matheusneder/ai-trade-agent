# SigNoz dashboard smoke tests

End-to-end tests of the four SigNoz dashboards generated by
[`scripts/signoz_dashboards.py`](../../scripts/signoz_dashboards.py): an ephemeral SigNoz is
started, a credential is created, the dashboards are applied, a synthetic day of the agent's
telemetry is sent, and Chromium (Playwright) checks every dashboard, panel and value.

> **Keep these tests in step with the dashboards.**
>
> - Every change to an existing dashboard requires running these tests and adjusting them to
>   the change (renamed panels, new series, other units or formats).
> - Every new chart, metric, indicator or feature comes with more test coverage: the seed
>   must emit what the new panel reads, and its expected values go into
>   `test_dashboards.py` (`EXPECTED_NUMBERS`, `EXPECTED_LEGENDS`, `EXPECTED_ROWS`).
> - The tests evolve with the dashboards: a dashboard change is not done until this suite is
>   green with it.

## Running

Requirements: Docker running (Rancher Desktop or Docker Desktop, with internet access to pull
the images on the first run) and Chromium for Playwright, installed once:

```bash
uv sync
uv run playwright install chromium
```

Then:

```bash
uv run pytest tests/signoz-dashboard-smoke-tests            # everything (~7 min)
uv run pytest tests/signoz-dashboard-smoke-tests -m signoz  # the same, by marker
uv run pytest tests/signoz-dashboard-smoke-tests/test_dashboards.py -k llm   # a subset
uv run pytest tests/signoz-dashboard-smoke-tests --headed --slowmo 300       # watch it
```

In VS Code, the Testing panel (Python extension, pytest; `.vscode/settings.json` enables it)
lists the suite under `tests/signoz-dashboard-smoke-tests`: one click on the folder, a file or
a test runs it.

The default `uv run pytest` does **not** run the e2e tests (no Docker, no browser): the
`conftest.py` here deselects the tests marked `signoz` unless the run names this folder (or a
file or test inside it) or selects the marker (`-m signoz` or `-m e2e`). Only `test_seed.py`
(the generator alone, a few seconds) runs by default.

Variables:

| Variable | Default | Effect |
| --- | --- | --- |
| `SIGNOZ_SMOKE_SEED` | `7` | seed of the synthetic data |
| `SIGNOZ_SMOKE_HOURS` | `24` | length of the seeded window (≥ 4) |
| `SIGNOZ_SMOKE_KEEP` | unset | `1` leaves the stack running after the tests |

Playwright's own options work too (`--browser`, `--headed`, `--tracing retain-on-failure`,
`--screenshot only-on-failure`, `--output`).

To explore the ephemeral SigNoz by hand (prints the URL and a throwaway login):

```bash
uv run python tests/signoz-dashboard-smoke-tests/smoke.py up
uv run python tests/signoz-dashboard-smoke-tests/smoke.py seed --seed 42 --hours 48
uv run python tests/signoz-dashboard-smoke-tests/smoke.py generate --seed 42 --out summary.json
uv run python tests/signoz-dashboard-smoke-tests/smoke.py down
```

## Layout

```
tests/signoz-dashboard-smoke-tests/
  compose.override.yaml   isolates Foundry's manifests (deploy/signoz/pours) for the tests
  conftest.py             fixtures: stack → credential → dashboards → seed; login per module
  smoke.py                manual control (up / seed / generate / down)
  test_seed.py            the generator alone (fast, runs in the default suite)
  test_stack.py           isolation guard, API key, provisioning, every query has data (API)
  test_dashboards.py      the dashboards in Chromium: loading, rendering, values, interaction
tests/support/signoz_smoke/   helpers (a package outside this folder: its name has dashes)
    environment.py        the ephemeral Compose project, its isolation check and readiness
    signoz.py             first admin, login, service account + API key, apply, ingestion wait
    seed.py               the deterministic synthetic day (spans, logs, metrics, Summary)
    otlp.py               OTLP/HTTP protobuf requests to the ephemeral ingester
    ui.py                 page objects (data-testid selectors) and the console/network watcher
```

## The ephemeral environment

`docker compose -p ta-signoz-smoke -f deploy/signoz/pours/deployment/compose.yaml -f
tests/signoz-dashboard-smoke-tests/compose.override.yaml`: SigNoz, ClickHouse, ClickHouse
Keeper, the PostgreSQL metastore, the schema migrator and the ingester, with the **same images,
versions and configuration files as `deploy/`** (the override only renames and rewires; a
version bump in `deploy/signoz` is picked up automatically).

Foundry's manifests pin the real stack's container, network and volume names and publish ports
8080/4317/4318 on every interface. The override gives everything its own name
(`ta-signoz-smoke-*`, network `ta-signoz-smoke-network`, project volumes) and publishes only
the UI and the ingester's OTLP/HTTP, on **random ports of 127.0.0.1**. Before starting,
`environment.Stack.up` renders the configuration and refuses to go on if any production name,
external network/volume or fixed port is still there (`test_stack.py` proves the check catches
the bare manifests). The production SigNoz, its ClickHouse and the agent's PostgreSQL are never
read, written, stopped or recreated.

One behavioral difference: the base manifests download ClickHouse's `histogramQuantile` user
function from GitHub and retry forever when GitHub is unreachable, which blocks ClickHouse. The
override keeps the same download with a short timeout and goes on without it; the dashboards
do not use it (it serves quantiles of metric histograms).

The session fixture runs `down -v` first (leftovers of an interrupted run), then `up --wait`,
waits for the migrator to exit successfully and for the API to answer, and at the end removes
containers and volumes. A whole start takes about a minute once the images are cached.

## The credential

A fresh SigNoz has no user; the first registration creates the organization and its admin,
with no e-mail or invitation. `tests/support/signoz_smoke/signoz.py` then automates the rest, with a random
password generated per run (never stored outside the session's temporary folder):

1. `POST /api/v1/register` — the first admin (`smoke-admin@example.test`);
2. `POST /api/v2/sessions/email_password` — a session token;
3. `POST /api/v1/service_accounts`, `POST /api/v1/service_account_roles` (`signoz-editor`) and
   `POST /api/v1/service_accounts/{id}/keys` — an API key with the Editor role, the same kind
   of key `scripts/signoz_dashboards.py --apply` uses in production (`SIGNOZ-API-KEY`).

The dashboards are applied with that key through `scripts.signoz_dashboards.apply`, the very
code of `--apply`. The browser logs in through the real login page once per session, and the
resulting local storage is reused by every test. No production credential or `.env` is read.

The ingester only turns on its receivers after SigNoz sends it a configuration over OpAMP, and
SigNoz does that only once an organization exists: the seed is sent after the registration.

## The synthetic data

`tests/support/signoz_smoke/seed.py` builds, with `random.Random(seed)` and no clock reads besides the
window's end, a full day (by default) of a normal operation of the agent, with the same service
names, span names, attributes, metric names and log fields the agent, Alloy and the
`docker_stats` collector produce:

- **traces** of each component (`trade-agent.runtime`, `.risk`, `.exchange`, `.db`, `.llm`...):
  the 1-minute risk check, reconciliation every 5 minutes, clock sync every 10, news ingestion
  every 15 and, every 4 hours (UTC), a decision cycle per profile with the analyst's three
  Claude calls; Binance calls carry the HTTP status and the used weight, and a few fail
  (HTTP 429/5xx);
- **metrics** `trade_agent.*`: the gauges every minute from one portfolio simulation (equity,
  peak, day start, drawdown, PnL per scope, exposure, positions, risk state per scope, error
  rate, weight, clock offset), and cumulative counters fed by the same events as the spans
  (LLM cost and tokens, cycles, entries, exits, risk state changes);
- **logs** as Alloy forwards them: structlog JSON bodies flattened into attributes, linked to
  their span by `trace_id`/`span_id`, plus the lines of Grafana, PostgreSQL, Loki, Alloy...;
- **container metrics** of the 14 compose services (CPU, memory, memory %, network, disk).

Activity follows the day: Binance traffic, latency and weight, CPU and log volume peak in the
afternoon (UTC) and bottom out at night. Rare events (an HTTP error, a failed task, a global
pause, a profile halt, an entry and a rule exit) are guaranteed at least once, so every panel
has data. The window ends on the current minute; `--end` (CLI) fixes it for a reproducible
dataset. The counters start at zero on the window's start, so the dashboards' `increase` over
the window adds up exactly what was recorded.

**Why OTLP, not inserts into ClickHouse:** the data goes through the real path — the SigNoz
ingester's receivers, processors (span metrics, LLM pricing) and ClickHouse exporters — so the
tables, materialized views, metadata (attribute keys) and time-series indexes are exactly the
ones production builds, and a schema change in a new SigNoz version needs no change here. The
collector keeps the timestamps it receives, so a past day can be sent in a few seconds. None of
the dashboards reads the span metrics the collector derives at ingestion time (with the current
clock), so nothing depends on when the seed was sent.

`Summary` holds what the dashboards must show (totals, last values, series names); the
dashboards are opened on the exact seeded window (`?startTime=…&endTime=…`), so counts match
exactly.

## What the tests check

- the stack is isolated; the API key has the Editor role and anonymous calls are refused;
- every dashboard of the generator is provisioned, and applying again updates in place;
- every panel query returns data over the seed (`signoz_dashboards.check`, the `--check` code);
- the dashboard list shows the four dashboards;
- each dashboard loads with its title, tag, sections and panel titles;
- every panel renders (chart with legend, number or table) with no error or "no data" state;
- number panels show the seeded values (equity, positions, requests, errors, LLM cost and
  tokens, containers...): counts exactly, decimals within one unit of the panel's last decimal
  (SigNoz truncates); legends list exactly the seeded series (the legend is a virtual list:
  it is scrolled to the end and checked against its "Showing N of M series" line); lists show
  the seeded rows and columns;
- the time range selector (6 h, 1 day, 1 hour) re-queries with the new range and changes the
  numbers; the refresh button re-queries; sections collapse and expand; a panel opens in the
  full-size view and closes; a legend entry hides and shows its series; the legend search
  filters the series; dashboard variables (none yet) render their selector;
- no console error, uncaught exception, failed request or HTTP 4xx/5xx from SigNoz during any
  UI test (`BrowserIssues`; only the license 404 of the community edition is allowed). Requests
  to other hosts (fonts, GitHub's latest release, SigNoz's changelog CMS) never leave the
  machine: they get a local answer in the shape the UI expects, so the browser part runs
  offline and those calls cannot add noise.

## When a dashboard changes

1. Edit `scripts/signoz_dashboards.py` and regenerate the JSON as usual.
2. Run `uv run pytest tests/signoz-dashboard-smoke-tests`.
3. New panel: rendering and error checks already cover it. Make the seed emit what it reads
   (`seed.py`), then add its expected value, series or rows to `test_dashboards.py` and, if
   it needs a new fact, a field to `Summary`. New interactive feature (variables, links...):
   add a test for it next to the interaction tests.
4. Changed panel: fix the expectations that no longer hold; never delete one without a
   replacement.
5. SigNoz upgrade: selectors live only in `tests/support/signoz_smoke/ui.py` and the API calls in
   `tests/support/signoz_smoke/signoz.py`.
